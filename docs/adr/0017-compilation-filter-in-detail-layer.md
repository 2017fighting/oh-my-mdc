# ADR-0017: 合集筛子全部下沉到详情层，三条判据各自留痕

- 状态：已接受（2026-11-17，取代 ADR-0016）
- 背景：#45 把 ADR-0016 的第一层量穿了。`main=s`（單體影片）不是「去掉合集」，而是「**只留恰好一位女优出演**」：12 位女优 3856 部，394 部「≥2 女优」的作品通过 `s` 的**正好 0 部**（含 `REBD-725` 这种两位女优的单体共演）；反过来，她自己带「精選綜合」的 BEST/総集編照样通过（每女优 3–46 部，`OFJE-186`、`IDBD-887` 类）。也就是说：用户要排除的两类，`s` 只捕到一类、还捕得过宽，而捕漏的那一类正是原设计留给详情层的。更关键的一条不是准不准，而是**它在上游静默地排**——被 `s` 排掉的作品连一句记录都不会留下，跳过表与「收下」那个出口对它们根本不可用。
- 决策：取数**取全集、不带 `s`**（`filter_by=0:a:{id}`）；筛子整体下沉到详情层，一次 `/api/v4/movies/{id}` 出三条判据，各自落 `subscription_skip`：`actors` 数 > 1 → `not_single`；类別「精選綜合」→ `compilation`；类別「4 小時以上作品」/「16 小時以上作品」→ `long_form`。`long_form` 是探针带来的新判据：`OFJE-665` 这类「她自己多部作品 12 小时」既无第二人、也不打「精選綜合」，只有时长类別能捕住。
- 考虑过的方案：**保留上游 `s`**——省一半详情请求（EvkJ 232→104），但它在静默地排，与「判据可以错，出口必须留」直接冲突，而且我们无法在面板上证明它排得对；**只让详情层排「精選綜合」**（#45 落地时的临时状态，已推翻）——等于完全不排共演，与用户「不要多人一起的」相反；**按番号前缀（`OFJE`/`PPX`）排除合集**——把上游命名习惯写成常量，改版即默默失效，与本仓「不硬编上游词表」同一理由。
- 后果：每部候选作品都多一次详情请求（回灌 30 天时几十次，并发 8 下十几秒，被水位线吃掉）；上游详情端点 2026-11 起匿名不可读（§13），开发环境的集成测试要用 fixture 或 token。误伤方向已接受：真正的四小时单体作品会被 `long_form` 当成合集——它在跳过表里看得见、能「收下」，这是三条判据都敢下得狠的前提。
