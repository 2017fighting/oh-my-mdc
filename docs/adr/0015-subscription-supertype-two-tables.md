# ADR-0015: 「订阅」是上位词，存储却是两张表

- 状态：已接受（2026-11-17）
- 背景：引入女优订阅之后，仓库里有两种东西在做同一件事——从上游产出一批待办作品：自建清单（`list_registry` 里 `purpose='want_watch'` 的那一行，`poll` 全量扫到底）与女优订阅（按水位线追新）。词上它们同属一类，所以 GLOSSARY 收了上位词「订阅」；存储上它们形状差得远：清单是一行 id + 用途 + 名字快照，女优订阅要带身份外键、水位线、回看窗口、启停与逐条回灌。
- 决策：**词上合并，表上不合并**。`list_registry` 原封不动留在设置域（向导、门禁「清单登记 / 清单验读」、`task.list_id` 外键都指着它），女优订阅另起 `subscription` + `subscription_skip` 两张表（§4.5），`task` 上加一列 `subscription_id` 与之并存。
- 考虑过的方案：**把 `list_registry` 泛化成一张 `subscription` 表**（加 `kind` 列）——形状最干净，但要同时改设置域的读写与 revision 指纹、门禁六判据里的两个、`task.list_id` 的外键目标，以及迁移 00005/00012/00014 已经赋予 `list_id` 的「手工/补录落 NULL」语义；**统一表 + 清单行外键引用旧表**——否决，同一件事出现两个可写位置，与本项目「设置没有第二条覆盖路径」的立场相抵。
- 后果：规格里必须写清「为什么上位词不合并表」，否则下一位读者会把它当重构靶子（这是本条存在的首要理由）。两种订阅的轮询节拍、限量与失败语义各自独立（§6.2），共用的是 ingest 而不是调度。将来若要加第三种来源（番号订阅、全站标签订阅），默认进 `subscription` 加 `kind`，而不是再起第三张表。
