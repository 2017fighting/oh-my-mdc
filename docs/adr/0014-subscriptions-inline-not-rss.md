# ADR-0014: 女优订阅并进流水线，不产出 RSS

- 状态：已接受（2026-11-17）
- 背景：`javdb_rss` 在 home-ops 已整机退役（那边的 ADR-0031），它活着的唯一理由是把 JavDB App 私有 API 渲染成 qBittorrent 能订的 RSS：`/rss/want.xml` 加三条 `/rss/actress/…`，qbt 的 `JAV` 规则再去拉。那套形态的代价全在边界上：qbt 加进来的种子不带本项目的 tag / category / savepath，只能靠「收编」（§6.1）事后补；状态真相分裂成两处（`pin.json` + `mteam.json` 在容器文件系统里，队列在 qbt 的 PVC 里），所以它必须自带一套首发冻结与手工重置的 runbook 才不重复下载。本项目这边的机械已经齐了：`poll` 会定源、先落库再加种、版本行以 infohash 为键——也就是 `pin.json` 想解决的「同一部作品 guid 要稳」在 DB 里天然成立。
- 决策：女优订阅**不产出任何 feed**，它是流水线的第二个待办来源。一条订阅每轮产出若干「待办作品」，之后与「想看清单」走完全相同的 ingest：定源 → 先落库 → 加种 → 置待删（订阅侧无清单项，故不触发）→ 刮削 → 入库 → 旁路副作用。qBittorrent 的 `JAV` RSS 规则保持删除，本项目也不注册任何 `/rss/*` 路由。
- 考虑过的方案：**复刻 RSS 输出**（改动最小、最贴近旧肌肉记忆）——否决，理由是把下载生命周期重新交给 qbt，等于把 ADR-0004（先落库再加种）与「DB 是状态真相」同时作废，并让「收编」从异常路径变成常态；**先出 RSS 过渡再内部化**——否决，中间态要同时维护两套语义（pin 稳定性与版本行稳定性），而这段中间态只服务一个人、持续几周。
- 后果：新增第四个循环（§6.2）并需要把 `poll` 里「定源 → 加种」抽成共用 ingest，否则两处各写一遍必然漂移；上游凭据、并发自帽、M-Team 优先级、失败退避全部复用，不再有「qbt 侧零配置、加个 URL 就订上」那种便利——加一位女优从此是面板上的一次写入，不是贴一条 URL。想翻案（重新产 RSS）要把 feed 渲染、`guid` 稳定性与 qbt 规则一起重造，并 supersede 本条。
