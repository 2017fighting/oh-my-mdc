# ADR-0011: 交付材料缺失 = 重取一次，永久失败才进需人工

- 状态：已接受（#36；细化规格 §5.2 / §6.1）
- 背景：`payload` 对 `delivery=torrent` 存的是 `.torrent` 的**备份路径**，而那份字节是瞬态的 —— 生产走 `/tmp` 的 emptyDir，reloader 每次改设置都会 Recreate 滚动 pod。备份消失之后，旧实现把「保留 `add_pending`、下轮再试」当成自愈，但那条路永远不会成功：文件不会再出现。于是每轮 poll 都以 error 收尾，`mdc_loop_last_success_unix_seconds{loop="poll"}` 冻结，40 分钟后 `MdcLoopStalled` 起来，而唯一能消掉它的是人工删掉那条版本行。
- 决策：
  1. **读不到备份就回 M-Team 重取一次**（按番号 `Resolve`），且**只认 infohash 与版本行相符的那条**。今天的选种策略可能与当初不同，站点上换了种子时它给出的是另一条版本的材料 —— 拿它加种会把两条版本混成一条。重取成功 → 落盘、把新路径写回 `payload`（人工重试与下一轮 poll 读的就是这一列）、照常加种。
     - 已知取舍：「取回这一条 infohash」只能做成「按番号取回今天最优的那条，下完核对 infohash」。M-Team 的搜索不给 infohash（只有下完字节才核得出来），要真正按 infohash 找就得逐条下载候选，那是拿唯一的瓶颈配额换一次边缘情形。
     - 重取**守 M-Team 的启停开关**：搜索与下载是唯一有配额的两种调用，禁用时给一条「启用后再重试」的永久失败，而不是每轮去撞一次。
  2. **重取也失败时按永久/瞬时分流**：永久（站点上已无该种、infohash 不符、凭据不对）→ `failed(downloading, reason)` 并**在同一条 UPDATE 里清掉 `add_pending`**（进 §8.2 需人工区）；瞬时（连不上、超时、设置域读不出来）→ 保持 `add_pending`，下一轮再试。
  3. **材料缺失不让 poll 这一轮变红**：永久失败已进需人工区，瞬时失败是上游的事（与「降级磁力不判循环失败」同一口径）。循环健康位要回答的是「poll 自己还跑得动吗」，不是「上游此刻可达吗」。
  4. 落盘、读回、重取、校验 infohash 归一个 `material` 模块，**poll 的自动加种与人工重试的重新加种共用它**：两条路读的是同一列 `payload`，就该对同一条版本有同一个理解（与 `qbittorrent.FromPayload` 作为「重新加种唯一实现」的既有裁决一致）。
- 后果：
  - 「改一次设置 + 一条 M-Team 版本正在加种」不再是永久卡死；最坏情况是一条版本进需人工区，并带着「备份读不到、重取也失败」的原因。
  - 重取最多多花一次 M-Team 下载配额，且**每次备份失效只花一次**（不是每轮一次）：重取成功就恢复了，永久失败就离开 pending。
  - 人工重试不再是一条死路：它对同一条版本做与 poll 相同的重取。
- 规格见 §5.2 / §6.1；术语见 GLOSSARY「交付材料」。
